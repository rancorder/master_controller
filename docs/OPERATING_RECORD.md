# 運用実績と障害分類

> **情報源:** システム運用者による申告  
> **記録日:** 2026-07-15

## 運用実績

本システムは、実運用において**約6カ月間、システム内部を原因とする不具合なく稼働している**。

ここでいう「システム内部を原因とする不具合」は、主に以下を指す。

- Master Controllerの停止・制御不能
- P1/P2実行サイクルの破綻
- SQLite競合による継続的な停止
- snapshot破損による監視不能
- subprocess管理の恒常的な不具合
- ChatWork通知基盤のシステム起因の停止
- 長期稼働による致命的なリソースリーク

したがって、現在のアーキテクチャにはコード上の改善余地や技術的負債はあるものの、**現行構成は6カ月の本番運用で安定性が実証されている**。改修時は、理論上より美しい設計へ全面置換することより、現在の安定挙動を壊さないことを優先する。

## 対象外となる外部要因

次の事象は、この「システム不具合なし」という実績には含めない。

- ショップ側のURL変更
- ショップ側のDOM・HTML構造変更
- セレクタ変更
- JavaScriptレンダリング方式の変更
- bot対策、CAPTCHA、アクセス制限
- 商品一覧の並び順変更
- 文字コードやレスポンス仕様変更
- 対象ショップの閉鎖・移転
- 外部APIやChatWork側の障害
- VPS・ネットワーク・OSなどインフラ側の障害

これらは**外部サイト仕様変更／外部サービス障害**として分類し、Master Controller本体の障害と分けて記録する。

## 改修時の判断原則

1. **6カ月安定稼働している挙動を正とする。**
2. コード上の懸念は、実障害が発生した事実と混同しない。
3. 改善は契約テストを追加してから、小さな単位で行う。
4. サイト個別のURL・DOM変更対応と、共通基盤のリファクタリングを同じ変更へ混在させない。
5. 不具合報告では原因を次の4分類で記録する。

| 分類 | 例 |
|---|---|
| システム内部 | scheduler、snapshot、SQLite、parser、通知制御 |
| ショップ仕様変更 | URL、DOM、セレクタ、並び順、売切表示 |
| 外部サービス | ChatWork、DNS、接続先CDN |
| インフラ | VPS、OS、ディスク、メモリ、ネットワーク |

## AIエージェントへの注意

Codex・Claude Codeは、静的解析で改善候補を発見しても、それを「過去に不具合が発生している」と表現してはならない。

正しい表現例:

> 現行実装には終了コード契約などの潜在的な改善点がある。一方、運用者によれば約6カ月間、システム内部を原因とする不具合は発生していない。

避ける表現例:

> 現行システムは不安定であり、障害が頻発する。

実運用実績とコード上の潜在リスクを分けて評価すること。
